Fleet maintenance: revert and update awareness

Operators can revert a lab VM directly from the fleet card instead of authoring a throwaway test plan. Same PowerShell script, same snapshot, same post-revert prep — just a second entry point into one shared operation. Sections 1–5 cover operator-initiated revert; sections 6–10 cover Windows update detection and notification. Regions R1–R24 map to the Copilot prompts in the companion spec.

R15Fleet banner, one row per severity, not one per node. Reboot-required is amber and states the consequence in operator terms — "no new work will be sent" — rather than naming an enum. Pending-only is informational blue and says the node still works.
R16Notification bell in the Agents title bar with an unread count. This is the only element that persists a history of update events across panel tabs.
R17Card shield badge. Blue shield = updates pending, node still dispatchable. Amber shield = reboot required. Clicking the badge opens the flyout (R18); the badge is the only new click target on the card.
R18Update flyout lists the actual KBs with per-item result, so a failed servicing-stack update is visible rather than buried. Sourced from event log payloads the agent already parsed.
R20Actions live where the problem is. Reboot now and Revert instead both start a `MaintenanceOperation` through the same service as section 2 — an update notification is an entry point into the revert engine, not a dead end.
R21Draining is the third eligibility state: the node keeps its current run but receives no new work. Distinct grey-blue card, distinct from both Available and Maintenance.
R22Live toast when an event arrives while the app is open. Carries the same two primary actions so the operator can act without navigating.
R23Provenance line. Every update status names which detector saw it — event log, registry poll, or startup snapshot — and when the agent last reported. Without this, a stale status is indistinguishable from a current one.

R24Three states, three separate policies. Collapsing them into one "block on updates" switch is the tempting simplification and the wrong one — pending updates can sit for a fortnight, and blocking on them would idle the fleet for nothing.
R24Reboot automatically defaults off. An unattended reboot on a lab VM is how a warm GR configuration quietly disappears. Make the operator opt in.
