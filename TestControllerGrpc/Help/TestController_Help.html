1. What is TestController?

TestController is a centralized orchestration tool that helps you automate and manage tasks across multiple computers (called "Agents"). Think of it like a conductor leading an orchestra — TestController tells each Agent what commands to run, when to run them, and monitors the results.

What Can You Do With It?

🎯 Automate Tasks

  • Run scripts on remote machines
  • Execute build and deployment pipelines
  • Trigger batch operations across servers

📊 Monitor & Control

  • See real-time execution status
  • View detailed logs from all agents
  • Cancel or retry failed operations

Key Concepts

Term What It Means Example
Controller This application — the central command center Your desktop running TestController
Agent A remote computer running the Agent service A build server, test machine, or production server
WatchList An XML file containing all your automation definitions MyProject.watchlist.xml
WatchItem A single automation job (contains events and actions) "Deploy to Production" or "Run Unit Tests"

2. Quick Start Guide

Follow these steps to get up and running in 5 minutes:

1 Open TestController

Launch the application. You'll see the main window with a ribbon toolbar at the top, a tree panel on the left, and an agent panel on the right.

2 Register Your First Agent

In the right panel (Agent Panel):

  1. Enter a friendly name (e.g., "Build Server")
  2. Enter the agent address: http://servername:5200
  3. Click Register + Test

A green icon means the agent is connected! 🟢

3 Create a WatchItem

In the ribbon, click HOME tab → Add WatchItem:

  1. Give it a name (e.g., "Run Disk Cleanup")
  2. Right-click the new WatchItem → Add Event → Choose "Manual"
  3. Right-click the Event → Add Action
  4. Configure the action with your command
4 Run It!

Select your WatchItem in the tree, then click Execute in the EXECUTION tab. Watch the progress in the Execution Log panel at the bottom!

Save your WatchList frequently using Ctrl+S. Your configurations are stored in an XML file that you can back up, share, or version control.

4. Setting Up Agents

What is an Agent?

An Agent is the TestAgentGrpc service running on a remote computer. It receives commands from the Controller and executes them locally on that machine.

Adding a New Agent

1 Ensure the Agent Service is Running

On the target machine, the TestAgentGrpc service must be installed and running. The default port is 5200.

2 Register in the Controller

In the Agent Panel (right side):

  • Name: A friendly identifier (e.g., "Build-Server-01")
  • Address: The gRPC endpoint (e.g., http://buildserver:5200)

Click Register + Test

3 Verify Connection

Look for the status indicator:

  • 🟢 Green = Connected and healthy
  • 🟡 Yellow = Connected but high load or warnings
  • 🔴 Red = Disconnected or error
  • ⚪ Gray = Unknown (never tested)

Agent Panel Features

ButtonDescription
Test Check connectivity and get current metrics from the selected agent
Test All Test every registered agent at once
Diagnose Run full diagnostic (DNS lookup, TCP port check, gRPC connection, system snapshot)
Remove Unregister the selected agent

Self-Registration

Agents can automatically register themselves with the Controller if configured to do so. This is useful when deploying many agents — they announce themselves when they start up.

The Controller automatically polls all registered agents every 30 seconds to update their health status.

Troubleshooting Agent Connections

Agent shows Red/Disconnected
  • Verify the agent service is running on the remote machine
  • Check firewall rules allow port 5200 (or your configured port)
  • Ensure no network issues between Controller and Agent
  • Run Diagnose for detailed error information
Connection times out
  • The agent machine may be under heavy load
  • Network latency may be high — check NET metric in health strip
  • Try increasing timeout values in appsettings.json

5. Creating WatchItems

WatchItem Structure

A WatchItem is like a folder that contains everything needed to automate a task:

📦 WatchItem: "Deploy to Production"
 ├── 📁 Event: "Manual Trigger"
 │    ├── 📋 Initialize: Load server names from file
 │    ├── 📂 ActionGroup: "Deployment Steps"
 │    │    ├── ⚡ Action: Stop IIS
 │    │    ├── ⚡ Action: Copy files
 │    │    └── ⚡ Action: Start IIS
 │    └── 🔗 Ref: "Send Notification" (from Template)
 └── 📁 Event: "On File Created"
      └── ⚡ Action: Process new file

Step-by-Step: Create Your First WatchItem

1 Add the WatchItem

HOME tab → Click Add WatchItem → Enter a descriptive name

2 Add an Event (Trigger)

Right-click your WatchItem → Add Event

Choose the trigger type:

  • Manual: Run only when you click Execute
  • Created: Run when a new file appears in a folder
  • Changed: Run when a file is modified
  • Renamed: Run when a file is renamed
3 Add Actions

Right-click your Event → Add Action or Add Group

Configure each action with:

  • Tag: Friendly name for logs
  • Agent: Which machine runs this (or "Local" for the Controller machine)
  • Command: The actual command to execute
  • Arguments: Parameters passed to the command
  • Working Directory: Where the command runs from
4 Save Your Work

Press Ctrl+S or click Save in the ribbon

Action Configuration Options

Field Description Example
Tag Identifier shown in logs CopyFiles
Agent Target machine (dropdown of registered agents) Build-Server-01
Command Executable or script to run robocopy or C:\Scripts\deploy.ps1
Arguments Command-line arguments C:\Source C:\Dest /MIR
WorkDir Working directory for the command C:\MyProject
Timeout Maximum seconds before action is killed 300 (5 minutes)
ContinueOnError If true, continue to next action even if this fails true or false

Using Parameters (Initialize)

You can load values from a text file and use them as tokens in your commands:

1 Create a parameter file (e.g., servers.txt): 
ServerName=PROD-WEB-01
DatabaseServer=PROD-SQL-01
BackupPath=\\nas\backups
2 Add an Initialize node to your Event pointing to this file
3 Use tokens in your Actions: 
robocopy C:\Deploy \\[ServerName]\c$\inetpub /MIR

At runtime, [ServerName] becomes PROD-WEB-01

6. Working with Templates

What Are Templates?

Templates are reusable action sequences. Create them once, use them everywhere via <Ref> nodes.

Example: You have 10 WatchItems that all need to send an email notification when complete. Instead of copying the same email action 10 times, create a "Send Notification" template and reference it.

Creating a Template

1 Switch to Templates Tab

In the WatchList Tree, click the Templates tab next to "WatchList"

2 Add a Template

HOME tab → Add Template → Enter a unique name (e.g., SendNotification)

3 Add Actions to the Template

Right-click the template → Add Groups and Actions as needed

Using a Template (Adding a Ref)

1 In Any Event

Right-click → Add Ref

2 Select the Template

Choose from the dropdown which template to reference

When you update a Template, all Refs automatically use the new version!

8. Troubleshooting

Action fails with "Agent Unavailable"

The Agent service is not reachable. Try:

  1. Check if the Agent service is running on the remote machine
  2. Verify firewall allows inbound connections on port 5200
  3. Use Diagnose in the Agent Panel for details
  4. If the agent crashed, the Controller will auto-reboot it (if configured)
Command times out

The command took longer than the configured timeout. Solutions:

  1. Increase the Timeout value in the Action properties
  2. Check if the command is stuck (hanging process on agent)
  3. Review the command for infinite loops or waiting on input
Parameters not resolving

Tokens like [ServerName] appear literally instead of being replaced:

  1. Ensure an Initialize node exists in the Event with the parameter file
  2. Check the parameter file format: Key=Value (one per line)
  3. Verify the token name matches exactly (case-sensitive)
  4. Place Initialize before the Actions that use it in the tree
Template changes not applying

After editing a Template, Refs might show old behavior:

  1. Save the WatchList (Ctrl+S)
  2. Click Refresh in the HOME tab
  3. Verify the Edit link in the Ref is pointing to the correct template
Cannot save WatchList

File save operations fail:

  1. Check if the file is open in another application
  2. Verify you have write permissions to the folder
  3. Try Save As to a different location
  4. Check if the file is read-only
Actions run but nothing happens

Command executes but expected results are missing:

  1. Check the Execution Log for actual output
  2. Verify the Working Directory is correct
  3. Test the command manually on the Agent machine
  4. Ensure paths and arguments are quoted if they contain spaces

11. Security Features

TestController supports multiple security modes to fit your environment — from development labs with no authentication to production environments requiring Active Directory integration and TLS encryption.

Authentication Modes

Mode Best For How It Works
None Development, isolated test labs No authentication — all requests treated as Admin. Never use in production!
Domain Enterprise environments with Active Directory Windows Negotiate (Kerberos/NTLM) authentication. Roles assigned by AD group membership.
Local Standalone servers, workgroups Local Windows accounts (SAM database). Admin role via local Administrators group.
Token API automation, service accounts Bearer token authentication. Tokens stored encrypted with DPAPI.

Setting Up Domain Authentication

1 Configure appsettings.json 
{
  "Security": {
    "Mode": "Domain",
    "Domain": {
      "DomainName": "YOURDOMAIN",
      "AdminGroups": ["Domain Admins", "TestController-Admins"],
      "UserGroups": ["Domain Users", "TestController-Users"],
      "FallbackToLocalOnDomainFailure": true,
      "GroupCacheTtlMinutes": 15
    }
  }
}
2 Create AD Security Groups

In Active Directory, create groups like:

  • TestController-Admins — Full access (execute, configure, manage agents)
  • TestController-Users — Read-only access (view status, logs)
3 Add Users to Groups

Add your team members to the appropriate groups. Changes may take up to 15 minutes to propagate (configurable via GroupCacheTtlMinutes).

If the domain controller is unreachable, the system can fall back to Local mode authentication when FallbackToLocalOnDomainFailure is enabled.

Setting Up Token Authentication

Token mode is ideal for automation scripts and service accounts that can't use Windows authentication.

1 Configure Token Mode 
{
  "Security": {
    "Mode": "Token",
    "Token": {
      "TokenStorePath": "C:\\ProgramData\\TestController\\tokens.encrypted",
      "TokenRotationDays": 90,
      "EnforceHttps": true
    }
  }
}
2 Generate Tokens

Use the admin endpoint to create tokens:

POST /api/security/tokens
{
  "name": "BuildServer-ServiceAccount",
  "role": "Admin",
  "expiresInDays": 365
}
3 Use in API Calls 
Authorization: Bearer eyJhbGciOi...
Always enable EnforceHttps in production to prevent token interception!

TLS/Transport Security

Encrypt all communication between Controller and Agents using TLS:

Mode Description When to Use
Plaintext No encryption (default) Isolated labs, development only
PlaintextAndTls Both ports active (5200 + 5443) Migration period — rolling out TLS gradually
TlsOnly Only TLS connections accepted Production environments

Enabling TLS on the Agent

{
  "AgentKestrel": {
    "EnableTls": true,
    "TlsPort": 5443,
    "CertificatePath": "C:\\Certs\\agent.pfx",
    "CertificatePassword": "your-password"
  }
}

Enabling TLS on the Controller

{
  "TransportSecurity": {
    "Mode": "TlsOnly",
    "CertificatePath": "C:\\Certs\\controller.pfx",
    "CertificatePassword": "your-password",
    "ValidateServerCertificate": true
  }
}

Mutual TLS (mTLS)

For maximum security, require both Controller and Agent to present certificates:

{
  "TransportSecurity": {
    "Mode": "TlsOnly",
    "RequireMutualTls": true,
    "TrustedCaThumbprint": "ABC123...",
    "ClientCertificatePath": "C:\\Certs\\client.pfx"
  }
}
With mTLS, unauthorized clients cannot connect even if they know the endpoint address. Both sides must have certificates signed by your trusted CA.

Security Audit Logging

All security-relevant events are logged:

  • Authentication — Login attempts (success/failure), token usage
  • Authorization — Permission checks, role evaluations
  • Admin Actions — Agent registration, configuration changes
  • Command Rejections — Blocked commands due to policy

Diagnostic Endpoints

Endpoint Auth Required Purpose
GET /api/security/status No Current security mode and health
GET /api/security/whoami User Your current identity, roles, permissions
GET /api/security/readiness Admin Full diagnostic report (AD connectivity, cert status)
GET /healthz/ready No Infrastructure health for load balancers

12. Role-Based Access Control (RBAC)

Section 11 covers authentication — proving who a user is. Role-Based Access Control answers the next question: once someone is signed in, what are they allowed to do? RBAC gives each user a role, and each role grants a specific set of permissions for triggering pipelines, editing the WatchList, managing agents, and viewing the audit trail.

RBAC is server-enforced. The web client hides or disables buttons based on your role, but the Controller re-checks every write request on the server — so permissions can't be bypassed by tampering with the browser UI.

How RBAC Fits With Authentication

Your identity comes from the authentication mode you set up in Section 11 (Domain, Local, or Token). RBAC then maps that identity to a role and a permission set stored in the Controller's RBAC database.

  • The WPF Controller (the desktop app) is the sole owner of the RBAC database. All roles and permissions are created and edited there.
  • Changes are pushed live to every connected web client over SignalR — no page reload or service restart required.
  • Reads are open; writes are gated. Anyone signed in can view status, logs, and results. Only actions — trigger, cancel, edit, configure, manage agents — require permission.

The Built-In Roles

RoleIntended ForWhat They Can DoWhere
Administrator System owners Everything: manage roles & permissions, register agents, change configuration, and view the audit trail WPF Controller only
Senior Manager Leads who run the whole suite Full operator rights — trigger and cancel any pipeline, view everything Web + WPF
Engineer Team members who own specific pipelines Trigger and cancel only their assigned pipelines; view-only everywhere else Web + WPF
Guest Observers, dashboards, stakeholders Read-only — view status and results via an anonymous session token; cannot trigger anything Web
The Administrator role signs in through the desktop Controller only — there is no admin login on the web client, by design. This keeps database ownership and audit access on a single trusted surface.

Permission States in the Web Client

In the web client's WatchList tree, every node shows one of three states so a user can tell at a glance what they're allowed to do. The legend at the top of the tree matches these:

StateWhat It MeansTrigger Button
Triggerable Your role has trigger rights on this pipeline Active
View only You can see the item and its results, but your role can't trigger it Hidden / inactive
Admin-disabled An administrator has disabled this item for everyone Disabled for all roles
Because permission changes broadcast over SignalR, when an administrator changes a role or disables an item in the Controller, connected web clients re-render these states within moments — no reload needed.

Configuring RBAC — Step by Step

RBAC is set up by an administrator from the WPF Controller. A typical first-time configuration:

1 Enable authorization in configuration

Add an Authorization block to the Controller's appsettings.json, alongside the Security block from Section 11:

{
  "Authorization": {
    "Enabled": true,
    "DefaultRole": "Guest",
    "DatabasePath": "C:\\ProgramData\\TestController\\rbac.db"
  }
}

Restart the Controller so the RBAC database initializes.

2 Sign in as Administrator (desktop)

Launch the WPF Controller and sign in with an account that resolves to the Administrator role. The RBAC management screens are available only here.

3 Assign roles to users

Open the security / roles area in the Controller and give each user (or authenticated identity) one of the four built-in roles. Until a user is assigned a role, they fall back to the default role set in step 1.

4 Scope Engineers to their pipelines

For each Engineer, select the WatchItems (pipelines) they own. They'll be able to trigger and cancel those, and will see everything else as view-only.

5 (Optional) Disable items for everyone

Mark any WatchItem as admin-disabled to lock it out for all roles — handy for retiring a pipeline or freezing it during maintenance without deleting it.

You can verify any user's effective permissions at any time with GET /api/security/whoami, which returns their identity, role, and resolved permissions (see Section 11, Diagnostic Endpoints).

Default Mode

Default Mode governs what an authenticated user can do before an administrator has assigned them a role — for example, on a freshly configured Controller. The role named in DefaultRole is applied to every unassigned identity.

Set DefaultRole to the least privilege appropriate for your environment — usually Guest (read-only). A permissive default means anyone who authenticates can trigger pipelines until you explicitly restrict them.

Auditing RBAC Activity

RBAC decisions feed the same audit trail described in Section 11. Recorded events include:

  • Role assignments and changes — who changed whose role, and when
  • Permission checks — which write requests were allowed or denied
  • Command rejections — actions blocked because the caller's role lacked permission
The audit trail is viewable by Administrators and only from the WPF Controller — it is not exposed on the web client.

RBAC Troubleshooting

A user can see a pipeline but the Trigger button is missing

That node is in the View only state — their role doesn't have trigger rights for it. If they should be able to run it, assign them as an Engineer scoped to that pipeline, or grant the Senior Manager role for full operator rights.

I changed a role but the web client still shows the old permissions

Permission changes broadcast over SignalR and normally apply within seconds. If a client isn't updating, its SignalR connection to the Controller has likely dropped — check the Online/Offline indicator in the web client header. Reloading the page forces a fresh permission fetch.

Why can't I log in as Administrator on the web client?

This is intentional. Administrator access — including role management and audit viewing — is restricted to the desktop WPF Controller so that database ownership stays on one trusted surface. Use the Controller for any admin task.

Every item shows as view-only or disabled

The Controller is probably running with no roles assigned yet, so every authenticated user falls back to the DefaultRole (Default Mode). Sign in as Administrator on the desktop and assign roles as described above.

RBAC controls authorization, not encryption. In production, always pair it with a real authentication mode and TLS (Section 11). Note that Security.Mode = "None" treats every caller as Admin and effectively bypasses RBAC.

13. Common Execution Issues

This section covers the most frequent problems encountered during execution and how to resolve them.

Connection & Communication Errors

UNAVAILABLE — Agent Unreachable

Symptoms:

  • Actions fail with "Agent Unavailable" or "UNAVAILABLE" status
  • Agent shows red in the Agent Panel
  • Execution log shows gRPC connection errors

Causes & Solutions:

CauseSolution
Agent service not running Start the TestAgentGrpc service on the remote machine
Firewall blocking port 5200 Open inbound TCP 5200 in Windows Firewall
Agent crashed Check Windows Event Log; Controller will auto-reboot if AutoRebootOnUnavailable is enabled
Network issues Run Diagnose to check DNS and TCP connectivity
The Controller automatically attempts to reboot unresponsive agents via Windows RPC when gRPC is down.
DEADLINE_EXCEEDED — Command Timeout

Symptoms:

  • Action shows "Deadline Exceeded" after running for some time
  • Command was killed before completion

Causes & Solutions:

CauseSolution
Command takes longer than timeout Increase Timeout in the Action properties
Command is stuck (infinite loop, waiting for input) Fix the command to not require interactive input; add timeouts to your scripts
Network timeouts Increase CommandTimeoutSeconds in Controller config
CIRCUIT_OPEN — Circuit Breaker Tripped

Symptoms:

  • All requests to an agent fail immediately
  • Log shows "Circuit breaker is open"

What's Happening:

After multiple consecutive failures (50% failure rate over 30 seconds), the circuit breaker "opens" to prevent overwhelming a struggling agent.

Solutions:

  1. Wait for the break duration (default 15 seconds) — circuit will auto-reset
  2. Fix the underlying agent issue (restart service, free resources)
  3. Use Test button to manually verify agent health
CHANNEL_RESET_STORM — Rapid Disconnections

Symptoms:

  • Frequent "Channel reset" messages in logs
  • Performance degradation
  • Multiple agents showing intermittent connectivity

Causes:

  • Network instability (packet loss, high latency)
  • Load balancer or proxy issues
  • Agent machines under heavy load

Solutions:

  • Check network infrastructure
  • Increase KeepAlivePingDelaySeconds and KeepAlivePingTimeoutSeconds
  • Reduce concurrent sessions
  • Channel resets are now rate-limited (30s cooldown) to prevent storms

Authentication Errors

HTTP 401 — Authentication Failed
ScenarioSolution
Domain mode: Kerberos ticket expired Log out and back in, or run klist purge
Token mode: Invalid or expired token Generate a new token; check expiration date
Wrong security mode configured Verify Security:Mode matches your authentication method
Service Principal Name (SPN) issues Register SPNs for service accounts: setspn -S HTTP/servername domain\account
HTTP 403 — Authorization Denied
ScenarioSolution
User not in required AD group Add user to TestController-Admins or TestController-Users
Group membership cached Wait for cache expiry (GroupCacheTtlMinutes) or restart Controller
Token has insufficient role Generate new token with correct role (Admin vs User)
HTTP 429 — Rate Limited

Too many requests in a short time. Default limits:

  • RequestsPerMinute: 300 (regular users)
  • AdminRequestsPerMinute: 600 (admin operations)

Solutions:

  • Reduce polling frequency in automation scripts
  • Increase rate limits in configuration if legitimate traffic
  • Distribute load across time (don't trigger everything simultaneously)

Execution State Issues

STUCK — Session Won't Complete

Symptoms:

  • Session shows "Running" indefinitely
  • Cannot start new executions (lock held)
  • Cancel button doesn't work

Causes:

  • Agent crashed mid-execution
  • Network disconnect during command
  • Command process stuck on agent

Solutions:

  1. Wait for the Stuck Execution Watchdog (runs every 60s) to auto-reset
  2. Manually click Reset Status to clear indicators
  3. If agent-side lock is stuck, restart the TestAgentGrpc service
  4. Use ForceReady API endpoint for emergency reset
DOUBLE_RELEASE — Semaphore Error (Agent Crash)

Symptom: Agent service crashes with SemaphoreFullException

Root Cause: Race condition between command cancellation and completion releasing the execution lock twice.

Status: ✅ Fixed in current version. Agent now catches and ignores double-release attempts.

If You Still See This: Update to the latest TestAgentGrpc build.

Proper gRPC configuration is critical for reliable Controller-Agent communication, especially for long-running pipelines.

Recommended Controller Configuration

{
  "Controller": {
    "Timeouts": {
      "TestConnectionTimeoutSeconds": 5,
      "PingTimeoutSeconds": 3,
      "CommandTimeoutSeconds": 14400,
      "ChannelConnectTimeoutSeconds": 30,
      "KeepAlivePingDelaySeconds": 60,
      "KeepAlivePingTimeoutSeconds": 30,

      "RetryMaxAttempts": 3,
      "RetryDelaySeconds": 2,

      "UnavailableRecoverySeconds": 60,
      "AutoRebootOnUnavailable": true,

}

KeepAliveTimeoutMinutes Idle connection timeout 720 (12h) — keeps connections alive for long pipelines
DisableMinRequestBodyDataRate Don't kill slow incoming data true — prevents timeout for large file uploads
DisableMinResponseDataRate Don't kill slow outgoing data true — prevents killing streaming output from long tests

For Long-Running Pipelines (4+ Hours)

Long pipelines require specific tuning to prevent false timeouts and connection drops.
{
  "Controller": {
    "Timeouts": {
      "CommandTimeoutSeconds": 28800,
      "KeepAlivePingDelaySeconds": 30,
      "KeepAlivePingTimeoutSeconds": 60,
      "AutoRebootOnUnavailable": true,
      "AutoRebootRecoverySeconds": 300
    }
  }
}

With these settings:

  • Commands can run up to 8 hours
  • Keepalive pings every 30 seconds detect dead connections faster
  • If the agent crashes, it's automatically rebooted and the command is retried

15. Best Practices & Lessons Learned

Agent Deployment

✅ Do

  • Run TestAgentGrpc as a Windows Service (not console)
  • Use a dedicated service account with minimal permissions
  • Deploy agents to multiple machines for redundancy
  • Keep agents updated to match Controller version
  • Monitor agent health via the health metrics strip

❌ Don't

  • Run agent as Administrator unless absolutely required
  • Disable the Stuck Execution Watchdog
  • Use plaintext mode in production networks
  • Put all workload on a single agent
  • Ignore yellow/red health indicators

WatchList Design

✅ Do

  • Use descriptive Tags for actions (shows in logs)
  • Set reasonable timeouts per action
  • Use Templates for reusable command sequences
  • Enable ContinueOnError for non-critical steps
  • Store WatchList files in source control

❌ Don't

  • Create one massive ActionGroup with 100+ actions
  • Hard-code server names — use Initialize parameters
  • Leave default timeout (may be too short)
  • Duplicate actions when Templates would work
  • Forget to save frequently

Security Best Practices

Lessons from Production Incidents

Lesson 1: Always enable AutoRebootOnUnavailable

Incident: A 4-hour pipeline failed 10 minutes before completion because the agent crashed. Without auto-reboot, the entire pipeline had to be restarted manually.

Learning: With AutoRebootOnUnavailable: true, the Controller reboots the agent and automatically retries the failed command after recovery.

Lesson 2: Don't set timeouts too short

Incident: Build actions consistently failed at 5 minutes. Investigation showed the default timeout was 300 seconds, but builds took 7 minutes.

Learning: Measure your longest-running commands and set timeouts with 50% buffer. Better to timeout rarely than constantly.

Lesson 3: Test agent connectivity before big runs

Incident: Kicked off a full deployment, but one agent had a stale DNS entry. First failure happened 30 minutes in.

Learning: Click Test All in the Agent Panel before starting large executions. Fix any red agents first.

Lesson 4: Use Initialize files for environment-specific values

Incident: Commands worked in dev but failed in prod — server names were hard-coded.

Learning: Use [ServerName] tokens resolved from Initialize files. Different environments use different parameter files.

Lesson 5: Monitor the health metrics strip

Incident: Execution became slow and unreliable. Later discovered Controller machine had 95% CPU usage from unrelated processes.

Learning: The health strip shows CPU, Memory, Disk, and Network. If metrics are yellow/red, address the underlying issue before executing.

Performance Tuning Checklist

  • ☐ Set MaxConcurrentCommands based on agent CPU cores (typically 1-2)
  • ☐ Increase KeepAliveTimeoutMinutes for long-running sessions
  • ☐ Enable DisableMinRequestBodyDataRate and DisableMinResponseDataRate
  • ☐ Set appropriate CommandTimeoutSeconds for your longest operation
  • ☐ Configure CircuitBreakerBreakSeconds based on typical recovery time
  • ☐ Enable AutoRebootOnUnavailable for unattended operation
  • ☐ Distribute workload across multiple agents
  • ☐ Use SSD storage on agents for I/O-heavy commands

16. Glossary

Term Definition
Action A single command to be executed (e.g., run a script, copy files)
ActionGroup A container that holds multiple Actions that run in sequence
Agent A remote computer running the TestAgentGrpc service that executes commands
Controller This application (TestController) — the central management interface
Event A trigger that causes Actions to run (Manual, Created, Changed, Renamed)
gRPC The communication protocol used between Controller and Agents
Initialize A node that loads key-value parameters from a text file
Ref A reference to a Template (allows reusing action sequences)
Session A single execution run — may contain multiple Actions across multiple Agents
Template A reusable set of Actions that can be referenced from multiple WatchItems
Token A placeholder like [ServerName] that gets replaced with actual values at runtime
WatchItem A top-level automation job containing Events and their associated Actions
WatchList An XML file containing all WatchItems and Templates for a project
